# Il PM diventa un workflow a cicli, avviabile e fermabile; il verdetto lo esegue il workflow

## Contesto e problema
Il PM della spec 002 è una sessione Claude Code desktop che interroga GitHub ogni 60
secondi. Ha funzionato — dodici task fusi senza intervento — ma consuma token anche a
lavoro fermo e resta legato a una finestra aperta sul PC. Alessio vuole un PM che si accende
e si spegne, che non costi nulla quando non c'è niente da fare, e che la fucina costruisca da
sé con Spec Kit (spec 003).

## Opzioni considerate
1. Sessione desktop con un comando di pausa: resta un processo in ascolto, resta il costo
   dei sondaggi.
2. Workflow GitHub Actions svegliato dagli eventi (PR pronta, domanda, fusione), con
   l'abilitazione del workflow come interruttore e uno script di decisione deterministico
   che chiama il modello solo per revisionare o rispondere.
3. Cron periodico: esecuzioni a vuoto e ritardo, senza vantaggi rispetto agli eventi.

## Decisione
Opzione 2. Il PM è `pm-agent.yml`; il modello riceve una PR o una issue e produce un solo
file di verdetto; ogni effetto — fusione, chiusura, commenti, label, pubblicazione degli
ADR — lo esegue il workflow (P9). Lo script che sceglie cosa fare è una funzione pura
testata (P2). L'interruttore è `gh workflow enable | disable`, incapsulato in `pm.ps1`.

Con questa decisione l'eccezione a P4 registrata in
`2026-09-02-2100-pm-agent-fonde.md` — limitata alla spec 002 — si estende a **ogni spec
lavorata dal PM a cicli**, sui repo dove è installato. Restano i limiti: il PM si ferma su
sicurezza, token, permessi, costi e cambi di requisito; nessun bypass; ogni fusione è
tracciata nel rapporto e ogni decisione in un ADR.

## Conseguenze
Zero costo a lavoro fermo; una chiamata al modello per PR e per domanda; log per
esecuzione. Gli eventi accaduti a PM fermo vengono ripresi dal giro di recupero all'avvio.
La sessione desktop e il ruolo `pm-agent` a loop vengono ritirati alla chiusura della spec
003. Il pulsante Avvia/Ferma nel Registro è rinviato a una spec successiva.
